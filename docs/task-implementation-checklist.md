This checklist provides a useful set of checks for both task developer and the reviewer.

Use it to ensure the task meets all technical and quality requirements before being merged.

#### 1. Task Metadata (task.yaml)
- [ ] instance_id is unique and follows conventions.
- [ ] time_estimate correctly reflects human effort (<4h, <24h, or >24h). (Note: Task should take at least 12 hours for a human)
- [ ] before_commit is complete: valid sha pointing to the setup commit.
- [ ] Correct java_version.
- [ ] Accurate target_sdk.
- [ ] after_commit is complete with a valid sha.
- [ ] commands accurately build, unit test, and Android test the project cleanly.
- [ ] test_files accurately lists all test files. (This is critical for resetting changes made by the agent in these files)
#### 2. Task Instruction (description)
- [ ] Hand-written by a human domain expert.
- [ ] Explains the problem clearly as an issue.
- [ ] Does not contain "gotchas" or obscure implicit requirements not natively deducible from standard Android architecture.
- [ ] Does not use artificial hints or repetitive guidance.
#### 3. Environment & Setup (The "Before" Commit)
- [ ] The before_commit builds successfully using the documented commands in task.yaml.
- [ ] Any setup unrelated to the core task (framework dependencies, initializing new gradle modules) is already applied in this commit.
- [ ] All prior tests are passing.
- [ ] Target SDK levels and Kotlin versions are verifiable and correct.
#### 4. The Solution (The "After" Commit)
- [ ] The full solution is implemented cleanly.
- [ ] The after_commit builds successfully.
- [ ] All tests (old and new) pass seamlessly.
- [ ] Implemented in Kotlin.
- [ ] Touches multiple code files. Test files and Gradle files only count if the task explicitly demands their refactoring.
- [ ] golden.patch, test.patch, and Dockerfile have been successfully generated using the validation commands (uv run refresh_golden_patches and generate_docker_images.py).
#### 5. Test Coverage & Validation
- [ ] Tests ensure the issue is completely fixed.
- [ ] Tests are general enough that an alternative, valid approach by an agent will still pass.
- [ ] Tests do not check for behaviors not described in the instruction.
- [ ] (Optional/Recommended) If new classes or symbols are expected, a validate.sh bash script is included to flexibly verify implementation correctness over strict naming-dependency in a native JUnit/Espresso test.
- [ ] Echoes useful debug information about failures.
#### 6. AI Contamination & Local Validation
- [ ] The task description is hand-written and not generated by an LLM.
- [ ] If agentic tools assisted in creating tests or boilerplate solutions, the human author has rigorously vetted them for corner cases or overly simplistic assertions.
- [ ] The trajectory, patches, and results from local runs have been manually evaluated to ensure the task's correctness and difficulty.
#### 7. Submission
- [ ] Only one task is present in the CL.
